  ## Endpoints
  
  1. **Query**: POST /v1/knowledge/query (operationId knowledge_query)
     - Body: `input` (string, required; Cala QL or natural language), `return_entities` (bool, default true).
     - 200 response: `results` (array of free-form objects, shape set by the query), `entities` (array of EntityMention or null). Both are required.
     - Example result: {"company": "Amenitiz", "funding_amount": "€38.9M", "round_type": "Series B", "sector": "Hospitality SaaS", "year": 2025}.
  
  2. **Search (knowledge search)**: POST /v1/knowledge/search (operationId knowledge_search)
     - Body: `input` (required), `explainability` (bool, default true), `return_entities` (bool, default true).
     - 200 response (Answer): `content` (Markdown string), `explainability` (array of ReasoningSteps or null), `context` (array of KnowBit), `entities` (array of EntityMention or null). All four are required.
     - ReasoningSteps: `content` (string), `references` (array of KnowBit UUIDs that must match `context[].id`).
     - KnowBit: `id` (UUID), `content` (string), `origins` (array of Origin). Origin has `source` {name, url}, `document` {name, url}, and `breadcrumb` (array of strings, described as "always empty for compatibility").
  
  3. **Search Entities**: GET /v1/entities (operationId entity_search)
     - Query params: `name` (required, 1–100 chars), `entity_types` (array of enum values, default []), `limit` (integer, 1–100, default 20).
     - Example from the docs: GET /v1/entities?name=Tim+Cook&entity_types=Person
     - Response: `entities` (array of Entity: `id`, `name`, `entity_type`, `description` nullable). Ordered by relevance.
  
  4. **Entity Lookup**: POST /v1/entities/lookup (operationId entity_lookup)
     - Body: `id` as a single-key object such as {"lei": "..."}, or the top-level shorthand {"lei": "..."}. Exactly one scheme. `additionalProperties: false`.
     - Supported schemes: `cik` (zero-padded), `companies_house_uk_company_number`, `lei`, `rssd_id`, `siren`.
     - Response: an Entity stub (`id`, `name`, `entity_type`, `description`).
  
  5. **Entity Introspection**: GET /v1/entities/{entity_id}/introspection (operationId entity_introspection)
     - Path param: `entity_id` (UUID).

  ## Query language (Dot-Notation, used in Query and Search)
  
  No formal grammar is published. The QueryRequest description says: "Dot-Notation Syntax is not a strict grammar — there is no syntax to get wrong. An empty or fallback result means no match, not a syntax error." The documented rules are:
  - `.` navigates entity/topic → attribute → nested facet, e.g. `companies.industry`.
  - `=`, `!=`, `>`, `<`, `>=`, `<=` filter a facet.
  - `AND` / `OR` combine multiple values of the same field: `investors=A AND B`, `series=A OR B`. Different fields are chained with `.`.
  - `order_by=field ASC|DESC` and `limit=N` control which results surface, not just their order.
  - `return(f1, f2, ...)` projects the result to those fields. On Query it is a strict projection, and the docs say to always keep an identity field like `name`. On Search it focuses the answer.
  - Clauses can appear in any order.
  - Numeric fields can come back as approximate strings ("over 100M", "~206,753"). The docs say to synthesize rather than treat them as exact.
  
  Documented examples:
  - `companies.industry=fintech.founded_year>=2020`
  - `startups.location=Spain.funding>10M.funding<=50M` (from the Query page intro)
  - `people.role=CEO.company.industry=AI`
  - `people.role=CEO.company.industry=renewable_energy`
  
  Traversal: a chain such as `people.role=CEO.company.industry=AI` reads as a path (person → role CEO → company → industry). This is the only multi-hop form shown. There is no documented path, shortest-path, or hop-count syntax.

  ## Notable features
  
  - **Explainability**: Search returns ReasoningSteps, each with `references` to KnowBit IDs in `context`. This is a claim-to-evidence link, enabled by default.
  - **Source provenance**: Every KnowBit has `origins` with source and document URLs. Every entity property and relationship edge has dated `sources`.
  - **Temporal data**: Edges have `valid_since` and `valid_until` (e.g. board membership from 2014-02-28 to 2015-03-13). Numerical observations are time series with `time`, `value`, and an origin such as a 10-Q or 10-K from SEC.
  - **Numerical observations**: Indexed by taxonomy (e.g. us-gaap) with `unit`, `cadence`, and `description`. Projection requires the observation UUIDs.
  - **Coverage**: Entity types span business, people, law, sanctions, macro/FX, and healthcare/life sciences (drugs, clinical trials, genes, proteins).
  - **Identifiers**: Lookup accepts LEI, CIK, rssd_id, Companies House number, and SIREN.
  - **Projection is the efficient read**: The docs say the coarse read returns no relationships or observations, and that projecting by introspected names is "the most token-efficient read."
  - **Not documented**: People-movement feeds, news/events endpoints, webhooks, batch calls, and an explicit "people movements" feature do not appear in any page or in the spec. The Person type and IS_CEO_OF / IS_BOARD_MEMBER_OF edges are the closest match.
